# Forum review from the beginning — 31 October 2026

Reviewed the rendered text of **all 40 pages / 394 posts** in the [Premium Mod thread](https://forums.alliedmods.net/showthread.php?t=225876), in order, then compared technical reports with the supplied 2.0.2.1 development source and the current rewrite. Page numbering uses the forum's default ten posts per page. This includes the earlier pages that were outside the original page-35-onward review.

One limitation: [post 80](https://forums.alliedmods.net/showpost.php?p=2059428&postcount=80) contains only an old screenshot. Its image proxy returns **Not Found**, so its contents cannot be verified. The following reply discusses unused-variable/indentation warnings. Historical attachments, external bug trackers and private versions are not covered by this review. Reports about different versions are evidence of symptoms, not proof that a particular current source line caused them.

This register records the rc3/rc4 audit snapshot. **rc5 supersedes several policies after server feedback:** native one-at-a-time throwable regeneration, secondary clip coverage/cache refresh, WASD Pyro flight, unlimited Dead Ringer resource, higher metal capacity with a refill command, player chat tags, and up to three sentries (the two extras locked at level 1). See `RC5_SERVER_TEST.md` for the current test plan.

## Additional fixes made in rc4

1. **Premium respawn during sudden death.** [Post 155](https://forums.alliedmods.net/showpost.php?p=2077440&postcount=155) and [post 214](https://forums.alliedmods.net/showpost.php?p=2110868&postcount=214) report it. rc3 still explicitly allowed `RoundState_Stalemate`. rc4 excludes that phase at scheduling and again when the timer fires. A shared policy test covers every round state with the round active/inactive. Ordinary running rounds and preround remain the only eligible phases; Arena/MvM and other existing checks still apply. Valve's [round state implementation](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/shared/teamplayroundbased_gamerules.cpp) identifies the stalemate transition and its special round handling.
2. **Pyro flight interrupted by the shot cooldown.** [Posts 176–177](https://forums.alliedmods.net/showthread.php?t=225876&page=18) and [posts 190–191](https://forums.alliedmods.net/showthread.php?t=225876&page=20) describe flight failing on some servers. Independently of the unknown causes of those old reports, rc3 contained a concrete weakness: it applied one tick's recoil only when `m_flNextPrimaryAttack` was ready. A continuously firing flamethrower advances that timestamp between flame packets, so many movement ticks were skipped. rc4 checks the networked starting/firing state instead, keeps ammunition/attack checks, excludes secondary fire, and applies recoil each eligible tick. This follows Valve's [flamethrower implementation](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/shared/tf/tf_weapon_flamethrower.cpp) and [state enum](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/shared/tf/tf_weapon_flamethrower.h). This establishes a source correction, not that every historical flight failure had this cause.
3. **Scout ball reserves selected through the wrong metadata.** [Post 86](https://forums.alliedmods.net/showpost.php?p=2063297&postcount=86) reports the configured reserve not appearing. rc3 selected the primary-ammo field for both Jarate and melee balls. Valve's [bat implementation](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/shared/tf/tf_weapon_bat.cpp) explicitly reads/consumes `TF_AMMO_GRENADES1` for Sandman/Wrap Assassin balls. rc4 selects that checked player-ammo slot for these bats; Jarate retains its primary-ammo lookup. Tests include missing/melee primary metadata and an undersized ammo table. Confirm actual firing/reserve behavior in TF2.

Also hardened movement against the [early movement report in post 195](https://forums.alliedmods.net/showpost.php?p=2106623&postcount=195): bunnyhop/flight now leave players with `FL_FROZEN` or `TFCond_FreezeInput` alone. This does not establish which mechanism caused that historical report. The rewrite does not force a nonzero base movement speed during the engine's freeze period.

## Server verification for the new build

When updating rc3, replace `addons/sourcemod/plugins/premium.smx` with rc4. Keep your custom config and the corrected rc3 translation file; rc4 packages the same corrected translations. Do not overwrite server settings simply to take these gameplay fixes.

1. Confirm version with `sm_premium_diagnostics`.
2. Enter sudden death, kill an entitled player, and verify no forced respawn. Also enter sudden death while a respawn is already pending. Test round win, Arena and MvM afterward.
3. As Pyro, hold primary fire continuously while airborne, aiming down. Check a supported flamethrower with ammo, empty ammo, weapon switch, primary release, secondary fire/airblast, taunt/stun/frozen conditions, and both flag/trial access. Compare the intended tick rate. This is the first engine verification of the corrected continuous-flight path.
4. Set `premium_stunballs 3`, spawn with Sandman, throw balls and check the reserve; repeat with Wrap Assassin. Verify unrelated primary/secondary ammunition is unaffected. Restore your intended reserve afterward.
5. Test the remaining historical symptoms using `ACCEPTANCE.md`, especially unprivileged glow, colour/dark after death, bow variants, mediguns, Widowmaker, resupply, permissions, MySQL and a long-session soak.

The build compiles with warnings treated as errors. Automated checks execute shared SourcePawn policies/controllers and real SQLite queries. They do not execute TF2 physics, weapon logic, rendering, actual MySQL or other server plugins. This review is a traceable issue register, not a statement that every forum report has passed on your server.
